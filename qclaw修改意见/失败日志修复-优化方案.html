失败日志一键修复 - 优化方案

这个方案设计得不错，一键修复的思路清晰。我补充 6 个优化点和针对每个 failure reason 的个性化修复策略：

🔧 优化点

1. 批量修复（强烈推荐）

如果失败日志有 20 条，一个个点修复太慢。

建议：加一个「全部修复」按钮，服务端用队列串行处理（避免并发压力）。

// server.js
let fixQueue = [];

app.post('/api/refresh/fix-all', async (req, res) => {
  const failures = req.body.failures;  // [{url, company, reason}, ...]
  fixQueue = [...failures];
  
  res.json({ queued: fixQueue.length });
  
  // 串行处理
  while (fixQueue.length > 0) {
    const job = fixQueue.shift();
    await fixJob(job);
    await new Promise(r => setTimeout(r, 2000));  // 每条间隔 2s
  }
});

前端显示进度条：修复中 (5/20)...

2. 修复次数上限（防止无限重试）

同一个 URL 修复失败 3 次，自动标记为 unfixable，不再显示修复按钮。 
// server.js 修复失败时
if (job.retryCount >= 3) {
  job.unfixable = true;
}

前端：显示灰色的"已放弃"标签，提示用户删除种子。

3. Playwright 实例复用（性能优化）

每次修复都启动浏览器太重了。

建议：全局维护一个浏览器实例，修复时复用：

// server.js
let browser = null;

async function getBrowser() {
  if (!browser || !browser.isConnected()) {
    browser = await chromium.launch({ headless: true });
  }
  return browser;
}

// 修复时
const browser = await getBrowser();
const page = await browser.newPage();

4. 修复前预判（节省时间）

某些 reason 的修复成功率极低，可以提前告知用户：
reason 修复成功率预估 建议
empty_page 10% 直接建议删除（大概率下架）
login_required 0% 不显示修复按钮，提示手动登录
rate_limited 30% 建议等 10 分钟再试

前端在修复按钮旁显示：成功概率：低（约 10%）

5. 删除种子前确认

删除种子会影响"从列表页发现新岗位"的功能（如果未来实现了模式 B）。

建议：删除前弹窗确认：

删除种子数据会影响后续爬取。确认删除该岗位的种子数据吗？
[取消] [确认删除]

6. 修复历史记录（调试用）

把修复结果写入日志：

// _webapp/logs/fix_history.log
[2026-05-20 16:30] bytedance-123 | timeout | 重试失败 | 删除种子
[2026-05-20 16:35] alibaba-456 | empty_page | 重试成功 | jdText=1520字

🎯 每个 failure reason 的个性化修复策略

timeout — 页面加载超时

原因：网络慢、页面资源多、反爬延迟

修复策略：

await page.goto(url, { 
  waitUntil: 'domcontentloaded',  // 改用 DOMContentLoaded（不等图片）
  timeout: 30000 
});
await page.waitForTimeout(3000);  // 额外等 3s

如果还是失败：

  • 检查是否跳转到验证码页（page.url().includes('captcha')）
  • 如果是 → 建议用户手动访问该 URL
  • 如果不是 → 可能是网络问题，建议检查 VPN

empty_page — 页面内容不足

原因：岗位下架、登录墙、SPA 未渲染

修复策略：

await page.goto(url, { waitUntil: 'networkidle', timeout: 30000 });
await page.waitForTimeout(8000);  // 等 SPA 渲染

// 检查登录墙
if (await page.$('text=请登录')) {
  return { success: false, reason: 'login_required' };
}

// 检查下架
if (await page.$('text=岗位已关闭')) {
  return { success: false, reason: 'job_closed' };
}

如果还是失败： 99% 是下架或需要登录，直接建议删除种子。

network_error — 网络错误

原因：DNS 失败、连接超时、服务器错误

修复策略：

  • 先用 fetch(url) 测试是否能访问
  • 如果 404 → 建议删除（页面不存在）
  • 如果 503 → 建议等 5 分钟再试
  • 如果是 DNS 失败 → 检查网络设置

rate_limited — 反爬拦截（429/403）

原因：请求太频繁、IP 被封

修复策略：

// 加随机延迟
await page.goto(url, { waitUntil: 'domcontentloaded' });
await page.waitForTimeout(Math.random() * 5000 + 3000);  // 3-8s 随机延迟

如果还是失败：

  • 建议"等 10 分钟再试"
  • 或提示"该网站反爬严格，建议手动访问"

browser_error — Playwright 异常

原因：浏览器崩溃、内存不足、版本不兼容

修复策略：

  • 检查浏览器版本（npx playwright --version）
  • 尝试重启浏览器实例
  • 如果频繁出现 → 检查服务器内存使用

login_required — 需要登录（新增）

你原方案表格里没有这个，但很重要。

修复策略：

  • 不显示修复按钮
  • 显示提示："该岗位需要登录才能查看，请手动访问"
  • 提供 URL 链接让用户点击

selector_mismatch — 页面结构变化

原因：网站改版，CSS 选择器失效

修复策略：

  • 尝试备用选择器（建议在配置里维护多套选择器）
  • 如果都失败 → 提示"页面结构变化，需更新爬虫"

✅ 优化优先级总结

优化 优先级 工作量
批量修复 高 1 小时
修复次数上限 中 30 分钟
Playwright 实例复用 高 30 分钟
修复前预判 低 30 分钟
删除种子前确认 中 15 分钟
修复历史记录 低 30 分钟
