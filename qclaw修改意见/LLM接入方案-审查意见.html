LLM 接入方案 - 审查意见

方案整体设计完整，RAG 思路正确（工具式而非全量注入）。发现 4 个必须修复的问题 和 3 个优化点。

🔴 问题 1（必须修复）：工具调用循环可能无限等待

问题：你说"最多循环 5 次防止无限调用"，但没说超时怎么处理。
如果 DeepSeek API 卡住（网络问题、API 降级），前端会一直显示"AI 思考中..."，用户不知道发生了什么。

修复：加超时保护

// server.js POST /api/chat
const chatWithTimeout = async (messages, tools, timeoutMs = 30000) => {
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(), timeoutMs);

  try {
    const response = await fetch('https://api.deepseek.com/chat/completions', {
      method: 'POST',
      headers: { 'Authorization': `Bearer ${process.env.LLM_KEY}` },
      body: JSON.stringify({ model: 'deepseek-chat', messages, tools, stream: false }),
      signal: controller.signal
    });
    clearTimeout(timeout);
    return response;
  } catch (err) {
    clearTimeout(timeout);
    if (err.name === 'AbortError') {
      throw new Error('请求超时（30秒），请稍后重试');
    }
    throw err;
  }
};

前端也要加超时提示：

// ChatPanel.vue
const TIMEOUT_MS = 30000;

let timer = setTimeout(() => {
  showToast('AI 响应较慢，请耐心等待...', 'info');
}, TIMEOUT_MS);

// 收到第一个 token 后清除
onFirstToken(() => clearTimeout(timer));

🔴 问题 2（必须修复）：search_jobs 工具缺少分页

问题：你说"只返回匹配的前 5 条"，但用户可能需要第 6-10 条。
没有分页，用户只能看到前 5 条，无法获取全部结果。

修复：工具定义加 page/pageSize 参数

// 工具定义
{
  "name": "search_jobs",
  "parameters": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "company": { "type": "string" },
      "page": { "type": "number", "default": 1 },
      "pageSize": { "type": "number", "default": 5 }
    }
  }
}

前端显示"加载更多"按钮：

// LLM 返回结果后，前端检查是否还有更多
if (result.total > result.page * result.pageSize) {
  showLoadMoreButton();
}

🔴 问题 3（必须修复）：爬虫触发可能无效

问题：之前的代码审查发现，4/5 的爬虫（字节/阿里/腾讯/美团）是读本地种子数据，不会真的去网上爬。
如果用户说"帮我把字节跳动的岗位更新一下"，LLM 调用 trigger_crawl 工具，但爬完后数据没变化，用户会困惑。

修复：爬虫触发前先告知用户

// 工具返回
{
  "status": "warning",
  "message": "字节跳动爬虫当前为种子数据模式，可能不会发现新岗位。建议手动检查。",
  "details": "当前 4/5 的爬虫使用本地种子数据，刷新不会更新内容。"
}

或者：在 LLM 系统提示词里说明

// buildSystemPrompt()
const prompt = `...
注意：当前爬虫系统有已知限制：
- 字节跳动/阿里巴巴/腾讯/美团的爬虫使用本地种子数据，刷新可能不会发现新岗位
- 只有百度的爬虫会实时抓取网页
- 如果用户要求"更新岗位"，请先说明这个限制，再执行爬取
...`;

🔴 问题 4（必须修复）：生产环境聊天功能不可用

问题：你说"GitHub Pages 无后端，聊天功能仅开发模式可用"。 但你的"全功能公网部署方案"里说要用 Render.com 部署后端。
矛盾点：如果生产环境用 Render.com，那聊天功能应该可用啊？

两种可能的解释：

解释 含义 需要补充
解释 A：生产环境用 Render.com 聊天功能可用，但需要 Render.com 后端 需要说明开发 vs 生产环境如何切换
解释 B：生产环境只用 GitHub Pages 聊天功能不可用，只有本地开发能用 需要说明为什么生产环境不部署后端

建议：采用解释 A（生产环境用 Render.com）

// server.js
const isProduction = process.env.NODE_ENV === 'production';

// 开发环境：聊天功能可用
// 生产环境：聊天功能也可用（通过 Render.com）
// 唯一区别：生产环境需要 CORS 配置

app.use(cors({
  origin: isProduction ? 'https://your-github-pages-domain.com' : 'http://localhost:5173'
}));

🟡 优化点 1：COMPANY_ALIASES 应该动态加载

你说"COMPANY_ALIASES — 中文公司名 ↔ 英文 key 映射"，但这个是硬编码的。
如果后面加了新公司（如"华为"），需要重启服务才能生效。

建议：改为动态加载

// 动态从 companies.json 读取
function buildCompanyAliases() {
  const companies = JSON.parse(readFileSync('companies.json', 'utf-8'));
  const aliases = {};
  for (const [key, config] of Object.entries(companies)) {
    aliases[config.name] = key;           // "百度" -> "baidu"
    aliases[config.nameEn] = key;         // "Baidu" -> "baidu"
    aliases[key] = key;                   // "baidu" -> "baidu"
  }
  return aliases;
}

// 每次调用时动态构建（或 30 秒缓存）
let cachedAliases = null;
let lastAliasUpdate = 0;

function getCompanyAliases() {
  if (!cachedAliases || Date.now() - lastAliasUpdate > 30000) {
    cachedAliases = buildCompanyAliases();
    lastAliasUpdate = Date.now();
  }
  return cachedAliases;
}

🟡 优化点 2：SSE 连接断开后应该重连

前端用 SSE 接收流式回复，但没说如果连接断了怎么办。
可能原因：网络抖动、Render.com 休眠后唤醒、服务端崩溃。

建议：前端加 SSE 重连逻辑

// ChatPanel.vue
let retryCount = 0;
const MAX_RETRIES = 3;

function connectSSE() {
  const evtSource = new EventSource('/api/chat/sse');

  evtSource.onerror = () => {
    evtSource.close();
    if (retryCount < MAX_RETRIES) {
      retryCount++;
      setTimeout(connectSSE, 1000 * retryCount);  // 指数退避
    } else {
      showToast('连接已断开，请刷新页面', 'error');
    }
  };

  evtSource.onmessage = (event) => {
    retryCount = 0;  // 重置重试计数
    // 处理消息...
  };
}

🟡 优化点 3：工具调用应该并行化

LLM 可能一次返回多个工具调用（如同时调用 search_jobs 和 list_skills）。
当前方案是"执行工具 → 把结果塞回消息 → 再问 LLM"，这是串行的。

建议：并行执行多个工具调用

// server.js
if (response.choices[0].message.tool_calls) {
  const toolCalls = response.choices[0].message.tool_calls;

  // 并行执行所有工具调用
  const results = await Promise.all(
    toolCalls.map(tc => executeToolCall(tc))
  );

  // 把所有结果塞回消息
  messages.push(response.choices[0].message);
  for (const result of results) {
    messages.push({
      role: 'tool',
      tool_call_id: result.id,
      content: result.output
    });
  }

  // 再问 LLM
  // ...
}

✅ 总结

优先级 问题 修复方案
必须 工具调用循环可能无限等待 加 30 秒超时 + 前端超时提示
必须 search_jobs 缺少分页 加 page/pageSize 参数 + 前端"加载更多"
必须 爬虫触发可能无效（4/5 只读种子） 工具返回时告知用户限制 + 系统提示词说明
必须 生产环境聊天功能不可用（矛盾） 明确开发 vs 生产环境切换方案
建议 COMPANY_ALIASES 硬编码 改为动态加载（30 秒缓存）
建议 SSE 连接断开后不重连 前端加指数退避重连（最多 3 次）
建议 工具调用串行执行 改为并行执行（Promise.all）
结论：方案整体可行，RAG 设计正确。
最关键的必须修复问题是问题 3（爬虫触发可能无效），需要在 LLM 系统提示词里说明当前限制，避免用户期望过高。
