全功能公网部署方案 - 审查意见

整体方案可行，架构选型合理。但有 3 个安全问题 和 4 个待确认点 必须处理。

🔴 问题 1（必须修复）：GitHub Actions 缺少触发认证

问题：workflow_dispatch 触发器无任何认证，任何知道仓库名的人都可以触发爬虫。 恶意用户可以反复触发你的爬虫，消耗 GitHub Actions 分钟数，甚至用你的服务器 IP 发请求。

攻击场景：

# 攻击者在自己的服务器上执行
curl -X POST https://api.github.com/repos/YOUR_NAME/YOUR_REPO/actions/workflows/crawl.yml/dispatches \
  -H "Accept: application/vnd.github+json" \
  -d '{"ref":"main"}'

# 后果：
# - 爬虫被反复触发
# - GitHub Actions 分钟数被耗尽
# - 爬虫请求打到目标网站，你的 IP 被封

修复方案：PAT 双重校验

Step 1: GitHub Actions workflow 加校验

# _webapp/.github/workflows/crawl.yml
name: Crawl Jobs

on:
  workflow_dispatch:
    inputs:
      secret_token:
        description: 'Secret token for trigger verification'
        required: true

jobs:
  crawl:
    runs-on: ubuntu-latest
    steps:
      - name: Verify token
        if: inputs.secret_token != secrets.GITHUB_PAT
        run: |
          echo "ERROR: Invalid token"
          exit 1

      - name: Checkout code
        uses: actions/checkout@v4

      # ... 原有爬虫步骤

Step 2: Render server.js 触发时带 token

// server.js
app.post('/api/refresh', async (req, res) => {
  const token = process.env.GITHUB_PAT;

  await fetch(
    `https://api.github.com/repos/${owner}/${repo}/actions/workflows/crawl.yml/dispatches`,
    {
      method: 'POST',
      headers: {
        'Authorization': `Bearer ${token}`,
        'Accept': 'application/vnd.github+json',
        'X-GitHub-Api-Version': '2022-11-28'
      },
      body: JSON.stringify({
        ref: 'main',
        inputs: { secret_token: token }
      })
    }
  );
  // ...
});

🔴 问题 2（必须修复）：PAT 权限泄漏风险

问题：GitHub Personal Access Token = 完全仓库控制权。 如果 PAT 泄露，攻击者可以：删除仓库、窃取数据、植入恶意代码。

修复方案：最小权限原则

不要给的权限 原因
admin:repo_hook 太高，完全控制权
delete_repo 可以删除整个仓库
workflow（全部） 不需要，改用 PAT 触发

只给这两个权限：

repo (Full control of private repositories)
  - contents: read & write  ← 写 workflow dispatch
  - actions: read          ← 读取 workflow 状态

Render 仓库安全：

  • Render 部署的代码仓库不要设为 public
  • 否则 PAT 可能在 commit 历史、CI 日志里暴露
  • 定期轮换 PAT（建议每 3 个月）

🔴 问题 3（必须修复）：管理员功能对所有人开放

问题：技能管理、数据刷新 对任何人开放。 任何人可以：删你的技能、改你的数据、触发爬虫。

修复方案：简单密码保护

Step 1: Render 环境变量

ADMIN_PASSWORD = your_secret_password_here

Step 2: server.js 加认证中间件

// server.js
function adminAuth(req, res, next) {
  const token = req.headers['x-admin-token'];
  if (token !== process.env.ADMIN_PASSWORD) {
    return res.status(401).json({ error: 'Unauthorized' });
  }
  next();
};

// 所有管理端点加 auth
app.post('/api/refresh', adminAuth, async (req, res) => { ... });
app.post('/api/skills', adminAuth, async (req, res) => { ... });
app.delete('/api/skills', adminAuth, async (req, res) => { ... });

Step 3: 前端弹窗

<!-- App.vue -->
<div v-if="showAdminPassword" class="modal">
  <input v-model="adminPassword" type="password" placeholder="输入管理员密码">
  <button @click="verifyAdmin">确认</button>
</div>

// 验证通过后存 localStorage
localStorage.setItem('adminToken', token);
注意：这个方案安全性有限（密码在 localStorage 明文存储）。 适合：私人工具、少数人协作。 如果需要更高安全性，考虑 OAuth 登录。

🟡 待确认 1：Render 750h/月 用量

750h = 24h × 31天 = 744h，刚好覆盖 24/7。 但 Render 计费按 30 天算 = 720h，有 30h 缺口。

建议：

  • 在 Render Dashboard 开启用量提醒（>80% 时邮件通知）
  • 预留 5% 余量，实际控制在 700h/月以内
  • 如果超用：降级到付费计划（$7/月）或接受降级

🟡 待确认 2：冷启动 SSE 处理

Render 免费版 15 分钟无请求会休眠。首次唤醒需要 30 秒。 用户点刷新后看到 30 秒空白，不知道发生了什么。

修复方案：前端加唤醒提示

// App.vue
async function handleRefresh() {
  const response = await fetch('/api/refresh/start', {
    method: 'POST',
    headers: { 'X-Admin-Token': adminToken }
  });

  if (response.status === 202) {
    showToast('⏳ 服务正在唤醒，预计 30 秒内开始爬取...', 'info');
    // 继续监听 SSE
  }
}

// SSE 事件处理
const evtSource = new EventSource('/api/refresh/sse');
evtSource.onopen = () => {
  showToast('✅ 爬取已开始', 'success');
};

🟡 待确认 3：域名配置方案

需要确认 GitHub Pages 的域名类型。
类型 示例 配置方式
默认 username.github.io/repo 直接使用，无需额外配置
自定义 jobs.example.com Render 需要配置自定义域名 + SSL

如果用自定义域名：

1. Render Dashboard → 你的服务 → Settings → Custom Domains
2. 添加你的域名
3. Render 会生成验证 DNS 记录
4. 去你的 DNS 运营商添加 CNAME 记录
5. 等待 SSL 证书自动签发（约 5 分钟）

🟡 待确认 4：Gemini 请求频率限制

Gemini 免费 key 有 1500 次/天 限制。 如果用户量增加，可能在几小时内耗尽。

修复方案：前端 + 后端双重限制

后端（server.js）：

// 内存版简单限流（生产环境用 Redis）
const rateLimiter = new Map();  // ip -> {count, resetTime}

function rateLimit(ip, maxReq = 10, windowMs = 5 * 60 * 1000) {
  const now = Date.now();
  const record = rateLimiter.get(ip);

  if (!record || now > record.resetTime) {
    rateLimiter.set(ip, { count: 1, resetTime: now + windowMs });
    return true;
  }

  if (record.count >= maxReq) {
    return false;
  }

  record.count++;
  return true;
});

// /api/chat 端点加限制
app.post('/api/chat', async (req, res) => {
  const ip = req.ip;
  if (!rateLimit(ip, 10, 5 * 60 * 1000)) {
    return res.status(429).json({
      error: '请求过于频繁，请 5 分钟后再试'
    });
  }
  // ... Gemini 调用
});

前端：

✅ 总结

优先级 类型 问题/建议 处理方案
必须 安全 GitHub Actions 无触发认证 PAT Bearer Token 双重校验
必须 安全 PAT 权限过大 最小权限：repo(contents+actions)
必须 安全 管理员功能开放 加 ADMIN_PASSWORD 认证
建议 运维 Render 750h 用量 开启用量提醒，控制 700h/月
建议 体验 冷启动 SSE 空白 前端加"服务唤醒中"提示
确认 网络 域名配置方案 根据域名类型选择配置方式
建议 运维 Gemini 频率限制 前后端双重限流
结论：3 个安全问题必须在部署前修复，否则存在严重安全风险。 4 个待确认点为锦上添花，可以在上线后逐步完善。
