百度爬虫 SSR JSON 提取方案 - 审查意见

这个方案很有价值，直接从 SSR JSON 提取数据绕过了 Playwright 的反爬问题。发现 4 个问题 和 3 个优化点。

🔴 问题 1（必须修复）：正则提取 JSON 遇到嵌套对象会失败

问题：你写的正则 window.__INITIAL_DATA__\s*=\s*({.*?});\s*</script> 用非贪婪匹配 .*?， 但如果 JSON 中包含嵌套对象（如 listDetailData: [{...}, {...}]），会在第一个 } 就停止匹配，导致 JSON 截断、JSON.parse 失败。

原因：非贪婪匹配 .*? 找到第一个 } 就停，不管这个 } 是属于嵌套对象还是外层对象的结束。

修复：用大括号计数法替代简单正则

function extractSSRData(html) {
  // 找到 window.__INITIAL_DATA__ = 之后的位置
  const match = html.match(/window\.__INITIAL_DATA__\s*=\s*\{/);
  if (!match) return null;

  const start = match.index + match[0].length;
  let depth = 1;
  let end = start;

  // 大括号计数法：逐字符扫描
  while (end < html.length && depth > 0) {
    const ch = html[end];
    if (ch === '{') depth++;
    if (ch === '}') depth--;
    end++;
  }

  if (depth !== 0) {
    console.warn('[百度] SSR JSON 解析失败：大括号不匹配');
    return null;
  }

  try {
    const jsonStr = html.slice(start, end - 1);
    return JSON.parse(jsonStr);
  } catch (e) {
    console.warn('[百度] SSR JSON 解析失败:', e.message);
    return null;
  }
}
修复效果：无论 JSON 有多少层嵌套，都能正确解析到完整的对象。

🔴 问题 2（必须修复）：XSS 安全风险

问题：如果用 innerHTML 将 HTML 注入到 DOM 再读取 window.__INITIAL_DATA__， HTML 中的恶意脚本可能在解析 JSON 之前执行，造成 XSS 安全风险。

修复：直接用正则从 HTML 源码提取，不操作 DOM

上面的 extractSSRData(html) 函数已经做到了——直接用正则从 HTML 字符串提取，不涉及 DOM 操作，天然免疫 XSS。

🔴 问题 3（必须修复）：URL 格式需要验证

问题：https://talent.baidu.com/jobs/detail/${recruitType}/${postId} 这个 URL 格式是推测的， recruitType（如 GRADUATE）是否真的直接拼在 URL 里需要验证。

建议：先用浏览器打开几个百度岗位页面，验证 URL 格式：

1. 打开 https://talent.baidu.com/jobs/list
2. 点进一个岗位详情页
3. 看地址栏 URL 是什么格式
4. 记录 recruitType 字段值和 URL 的对应关系

可能的情况：

  • GRADUATE → /jobs/detail/graduate/2712b6b5-...
  • 或 GRADUATE → /jobs/detail/postId（不用 recruitType）
  • 或 URL 完全不是这个格式，需要从列表页的 detailUrl 字段获取
建议：SSR 数据里如果有 detailUrl 字段，优先用它；没有的话再自己构造。

🔴 问题 4（必须修复）：缺少 fallback 策略

问题：百度列表页可能偶尔不返回 window.__INITIAL_DATA__（SSR 未生效、CDN 缓存返回空壳等）， 方案没有说明这种情况怎么处理。

修复：

function parseSSRData(html) {
  const data = extractSSRData(html);
  if (!data || !data?.listData?.listDetailData) {
    console.warn('[百度] SSR 数据缺失，回退到旧解析器');
    return fallbackParseListPage(html);  // 保留旧的 parseListPage 作为兜底
  }
  // ... 正常逻辑
}

好处：即使 SSR 数据偶尔失效，也不会完全无法爬取。

🟡 优化点 1：name 字段可能包含 J-ID 后缀

问题：SSR 数据里的 name 字段包含"岗位标题 + J-ID"， 如"{title} (J-ID: BID-12345)"，直接用会污染岗位标题。

修复：

// 提取 title，去掉 J-ID 后缀
function cleanTitle(name) {
  return name
    .replace(/\s*\(?\s*J-ID:\s*\w+\s*\)?\s*$/i, '')  // 去掉 " (J-ID: BID-12345)"
    .replace(/\s*-\s*J\d+$/i, '')                     // 去掉 " - J123"
    .trim();
}

🟡 优化点 2：serviceCondition 可能为空

问题：部分岗位的 serviceCondition（任职要求）可能为空字符串或 null， 直接拼接会导致 JD 文本只有工作内容、没有任职要求，影响技能提取。

修复：

let jdText = workContent || '';
if (serviceCondition && serviceCondition.trim()) {
  jdText += '

职位要求
' + serviceCondition;
}
// 如果 serviceCondition 为空，至少有 workContent
