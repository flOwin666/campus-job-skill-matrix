两个架构问题

1. Vercel 现状 — 为什么不能用 Vercel

之前确实配置过 Vercel，但后来所有 API 文件都删除了。原因是：

  1. Vercel 国内被墙 — 不翻墙打不开 Vercel 的 serverless 函数
  2. 不需要 API — 技能管理和三色统计都改成了前端静态计算，不再依赖后端

当前后端状态

GitHub Pages 纯静态前端，不跑任何代码
Vercel 文件在但 API 全删了，等于没用
server.js 唯一能跑爬虫和聊天的后端，本地运行

结论

聊天和爬取需要实时计算（LLM调用+Playwright浏览器），不是静态操作。必须有一个后端在运行。如果不想用户跑 node server.js，就得把 server.js 部署到一台国内可访问的服务器上（阿里云轻量/腾讯云等，学生价 ~30元/月）。

2. 数据双向同步 — 用户爬取 vs 开发模式

当前数据读写路径

开发模式 (localhost:5173)
读取：public/jobsData.json
写入：src/jobsData.json（mergeJobs）
然后：syncJobsToPublic() 同步到 public/
用户聊天触发爬取 → mergeJobs 写到本地 → Vite 热更新 → 开发者立即看到 ✅
生产模式 (GitHub Pages)
读取：GitHub raw URL
写入：不能写（只读静态文件）
更新：需要 git push 到 _github-data
除非 chat crawl 后自动 git push → 否则生产用户看不到新数据 ❌

双向同步方案：GitHub 作为"中心数据库"

借助一个简单事实：数据只有一个"家"——GitHub，其他都是缓存。

操作 触发者 写到哪里
管理员全量刷新 管理员（设置面板） 本地文件 → merge → syncPublic → git push
用户聊天触发爬取 用户（聊天面板） 本地文件 → merge → syncPublic → git push（自动）
GitHub Actions 定时爬取 自动化（crawl.yml） 直接提交到 _github-data → git push
开发者模式加载 任何人打开 localhost 读 public/jobsData.json（本地缓存，可能< 1 分钟旧）
生产模式加载 任何人打开 GitHub Pages 读 GitHub raw（中心数据库，最新版本）

关键改进：所有写操作最终都 git push 到 GitHub。GitHub 是唯一的真相来源。

开发模式一致性：开发者打开 localhost 时，从 GitHub raw 拉一下最新数据（而不是依赖可能过期的本地 public/ 文件），确保和线上一致。

简化版数据流

聊天触发爬取 → mergeJobs + git push → GitHub（中心数据库） ⇄ 所有人可见

开发者 localhost 启动时从 GitHub 拉取最新数据，保证和线上一致
